# ADR 0013. Полнотекстовый поиск по актам (этап 6)

- Статус: принято
- Дата: 2026-10-24

## Решения

1. **Реестр на SQL PostgreSQL** (`NamedParameterJdbcTemplate`), а не JPQL: функции полнотекстового поиска (`@@`, `websearch_to_tsquery`, `ts_rank_cd`, `ts_headline`) в JPQL недоступны.
2. **`work_act.search_vector`** (`tsvector`, конфигурация `russian`, индекс GIN) пересобирается одним SQL в `refreshAggregates` после любого изменения акта: шапки, открытия, табеля, участников, запчастей, фото. Веса: A — номер и краткое описание; B — заказчик, площадка, подразделение, техника; C — подробное описание, рекомендации, место работ, представитель заказчика; D — ФИО инженеров, запчасти, подписи к фото. Миграция `V6` заполнила вектор для существующих актов.
3. **Запрос** разбирается `websearch_to_tsquery('russian', q)`: работают «точная фраза», `-исключить`, `or`. Русская морфология: «форсунками» находит «форсунок» и «форсунки». Дополнительно — поиск по части номера акта, серийного, гаражного, госномера и каталожных номеров запчастей (`LIKE` с триграммными индексами `pg_trgm`): номера пользователи вводят кусками, и стемминг их не разбирает.
4. **Порядок:** при поиске без явной сортировки — по релевантности `ts_rank_cd`, затем по дате; иначе — по выбранной колонке (номер, период, техника, заказчик, краткое описание, инженеры, часы, статус).
5. **Подсветка** — `ts_headline` по краткому и подробному описанию и рекомендациям, совпадения отмечены `[[…]]`; клиент выделяет их цветом.
6. **Новые фильтры:** площадка, часть каталожного номера запчасти («все акты, где ставили 1R-0750»), краткое описание (точно), наличие скана подписанного акта.
7. **Выгрузка реестра** — `GET /api/v1/acts/export` с теми же фильтрами, одна таблица Excel с автофильтром и закреплённой шапкой, до 5000 строк.
8. **Сохранённые наборы фильтров** хранятся в браузере пользователя (`localStorage`): они личные и не требуют серверной модели. Синхронизация между устройствами — в бэклоге.
