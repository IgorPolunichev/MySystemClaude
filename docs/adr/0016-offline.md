# ADR 0016. Офлайн-режим (этап 9.1)

- Статус: принято, реализуется по частям (9.1б — сделано, 9.1в — далее)
- Дата: 2026-10-25

## Решения

1. **Локальный слой внутри `apiFetch`.** Все запросы экранов проходят через одну функцию, поэтому офлайн встроен в одном месте, без правки экранов. Без связи чтение актов и справочников обслуживает локальная база (Dexie/IndexedDB), а изменения актов применяются на устройстве (`offline/apply.ts` — те же правила, что на сервере, включая расчёт времени из интервалов) и записываются в очередь (клиентский outbox). Изменения акта, у которого есть неотправленные операции, тоже идут в очередь — так сохраняется порядок.
2. **Синхронизация** (`offline/sync.ts`): при запуске, при появлении сети, каждые 2 минуты и по кнопке. Сначала очередь отправляется по порядку — сервер заново проверяет права и данные каждой операции; затем загружаются «мои акты для устройства» (`GET /api/v1/acts/device?days=90`: черновики, открытые и изменённые за 90 дней) и справочники.
3. **Справочники загружаются полностью** (техника, инженеры, организации и площадки, каталог запчастей, единицы, исполнители) раз в сутки или по кнопке, существующими постраничными запросами. Выгрузка изменений `updatedSince` и журналы удалённых записей (раздел 17.3 SPEC) отложены: при объёмах сервисной компании полная загрузка — десяток запросов; вернёмся к ним, если справочники вырастут (бэклог).
4. **Идентификаторы с клиента:** акты и строки запчастей получают UUID v7 на устройстве; повторная отправка операции не создаёт дубль (сервер идемпотентен с этапа 3). Черновик без связи получает временный номер `Ч-{код устройства}-{n}`; «Открыть акт» без связи ставит отметку «Открыть после синхронизации» — номер выдаёт сервер, пользователь получает уведомление.
5. **Конфликты:** последовательные правки шапки без связи отправляются от версии, которую вернул сервер на предыдущую. Если акт изменили на сервере (409), отправка правок этого акта останавливается, в журнале синхронизации — «Оставить моё» (отправить поверх текущей серверной версии) или «Взять с сервера» (отменить свои неотправленные правки этого акта). Отказ сервера (акт закрыт, нет прав) — «отклонено сервером», изменения остаются в журнале, пока пользователь их не уберёт.
6. **Интерфейс:** индикатор «Онлайн / Офлайн» в шапке со счётчиком неотправленных изменений; журнал синхронизации; выход из учётной записи очищает локальную базу и с неотправленными данными требует подтверждения.
7. **Без связи недоступны** (как в разделе 17.1): закрытие и возврат, Excel, письма, дашборд, администрирование, документы акта; экран показывает «Это действие доступно только при подключении к сети».

## Осталось (9.1в)

- Фото без связи: хранение в IndexedDB, загрузка в фоне с повторами, статусы «на устройстве / загружается / загружено».
- Офлайн-сессия 7 дней: сейчас без связи можно продолжать работу в уже открытом приложении; запуск приложения без связи требует сохранения входа на устройстве.
- Сравнение конфликта по полям («выбрать по каждому полю»).
- Предупреждение о заканчивающемся месте на устройстве.

## Уточнение заказчика (9.1в, часть А)

Выбран вариант «клиент на каждом ПК» (раздел 19.11 SPEC). Данные принадлежат ПК: справочники и акты не удаляются при выходе; ПК привязывается к заказчикам и площадкам — их акты загружаются на ПК; операции очереди помечены автором и отправляются только от его имени (сервер проверяет права автора). Локальный сервер площадки рассматривался и отклонён: его установка и обслуживание на каждой площадке дороже, чем польза при текущем числе ПК.

## Вход без связи (9.1в, часть Б)

Выбран ПИН-код на ПК (раздел 19.12 SPEC), а не «доверенный ПК без ввода»: на одном ПК работают несколько человек. Проверка — WebCrypto PBKDF2 на устройстве; хранится отпечаток. Перед переходом на страницу входа Keycloak приложение проверяет его доступность (`/.well-known/openid-configuration`), иначе браузер показал бы ошибку сети вместо приложения. Офлайн-сессия живёт до закрытия окна; роли и ФИО берутся из профиля, сохранённого при последнем входе со связью.

## Исправления после проверки заказчиком

- Синхронизация, вызванная до входа (ещё нет пропуска), оставляла внутренний флаг «синхронизация идёт», и все следующие вызовы ничего не делали — справочники и акты не загружались, очередь не отправлялась. Проверка пропуска вынесена до установки флага; добавлен тест.
- Со связью изменения больше не уходят в очередь только из-за того, что ранее один запрос не прошёл: сначала всегда пробуется сервер, в очередь — лишь при реальном сбое; если связь недавно пропадала, ожидание ответа сокращено до 4 секунд.
- Сценарий проверен в настоящем браузере (Chromium) с поддельным сервером: вход → справочники на ПК → «Настройки этого ПК» → акт со связью (очередь пуста) → связь пропала (акты видны, новый акт в очереди) → связь вернулась (очередь отправлена за ~15 с).
