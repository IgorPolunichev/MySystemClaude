# ADR 0004. Вход через Keycloak и проверка токенов

- Статус: принято
- Дата: 2026-10-23

## Контекст

Пользователи и роли хранятся в Keycloak (`SPEC.md`, раздел 3). Браузер обращается к Keycloak по адресу `http://localhost:8180`, а сервисы внутри Docker — по `http://keycloak:8080`. Если издатель токена зависит от адреса, проверка токена в сервисах ломается.

## Решение

- Realm `acts` импортируется при старте из `infra/keycloak/acts-realm.json`: роли `ENGINEER`, `DEPARTMENT_HEAD`, `ADMIN`, публичный клиент `acts-frontend` (Authorization Code + PKCE S256), тестовые пользователи.
- Keycloak запущен с `KC_HOSTNAME=http://localhost:8180` и `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`: издатель (`iss`) всегда внешний адрес, а внутренние запросы работают по имени контейнера.
- Сервисы и шлюз проверяют `iss` по `OIDC_ISSUER_URI` (внешний адрес), а ключи забирают по `OIDC_JWK_SET_URI` (внутренний адрес). Обращения к Keycloak при старте сервиса нет — ключи загружаются при первом запросе.
- Роли из `realm_access.roles` превращаются в `ROLE_*` (`KeycloakJwtAuthenticationConverter`); имя пользователя — `preferred_username`.
- Шлюз пропускает только аутентифицированные запросы к `/api/**`; права по ролям проверяют сервисы. Фронтенд читает роли из токена только для показа меню.

## Последствия

- Для продакшена: HTTPS, реальный `KC_HOSTNAME`, режим `start` вместо `start-dev`, отдельные секреты — в бэклоге.
- Учётные записи инженеров создаются в приложении, Keycloak хранит их (решение этапа 0 № 9) — реализуется на этапе 2.
