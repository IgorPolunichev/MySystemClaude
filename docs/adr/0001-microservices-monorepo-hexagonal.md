# ADR 0001. Микросервисы в монорепозитории, гексагональная архитектура внутри сервиса

- Статус: принято
- Дата: 2026-10-23

## Контекст

Заказчик выбрал микросервисы с первого дня (`docs/assumptions.md`, вопрос 1). Приложение будет расти модулями (уведомления, склад), и добавление модуля не должно требовать переписывания существующего кода (раздел 13 `SPEC.md`).

## Решение

- Один Git-репозиторий, один Maven-проект с модулями: общие модули в `platform/`, сервисы в `services/`.
- Восемь сервисов из раздела 4: `api-gateway` и семь доменных. У каждого доменного сервиса своя БД в общем экземпляре PostgreSQL (database-per-service); чужие БД сервис не читает.
- Внутри сервиса — пакеты `domain`, `application` (с `port.in`/`port.out`), `adapter.in.web`, `adapter.in.event`, `adapter.out.persistence`, `adapter.out.event`, `adapter.out.client`, `config`. Правила зависимостей проверяет `HexagonalArchitectureRules` (ArchUnit) в тесте каждого сервиса.
- Общие модули без бизнес-логики: `common-web` (безопасность, ошибки, correlation-id, пагинация), `common-events` (схемы событий), `common-test` (тестовая инфраструктура).
- В каждой БД с первой миграции есть таблицы `outbox` и `processed_event` — для надёжной публикации и идемпотентной обработки событий.

## Последствия

- Один `docker compose up` поднимает всё; одна сборка проверяет всё.
- Общая конфигурация безопасности подключается в сервисе явно (`@Import(CommonWebConfiguration.class)`), а не авто-конфигурацией: так она не зависит от порядка авто-конфигураций Spring Boot.
- Как расширять: новый модуль — новая папка в `services/`, строка в корневом `pom.xml`, маршруты в `api-gateway`, сервис в `docker-compose.yml`, база в `SERVICE_DATABASES`.
