# ADR 0010. Фото технического отчёта (этап 4)

- Статус: принято
- Дата: 2026-10-24

## Решения

1. **Загрузка через `media-service`, а не напрямую в хранилище.** Прямая загрузка по presigned URL требует CORS в RustFS и отдельного внешнего адреса хранилища для подписи ссылок — хрупкая настройка. Фото и так сжимаются в браузере до 1–2 МБ, поэтому проход через сервер дёшев. Presigned-загрузка вернётся вместе с офлайн-режимом, когда понадобится докачка крупных файлов.
2. **Подготовка в браузере** (`browser-image-compression`): до 2560 px по длинной стороне, JPEG ~85 %, поворот по EXIF применяется к пикселям, метаданные (включая геоданные) удаляются. Так сервер получает уже правильно повёрнутый снимок без EXIF и ему не нужна библиотека для разбора ориентации.
3. **Сервер** проверяет формат по сигнатуре (JPEG, PNG), размер (до 20 МБ), делает превью 400 px средствами JDK (ImageIO) и хранит оба файла в S3 (`act_photo/{actId}/{mediaId}.jpg` и `…-thumb.jpg`). Бакет создаётся при первом обращении.
4. **Выдача** — `GET /api/v1/media/{id}/content?variant=thumbnail|original` с токеном; браузер получает файл через `fetch` и показывает его как `blob:` (обычный `<img src>` не передаёт токен). Ответ кэшируется: содержимое по id не меняется.
5. **Связь с актом** — таблица `act_photo` в `act-service`: подпись, порядок, автор. Подпись можно добавить позже, но акт без подписей ко всем фото не закрывается. После закрытия фото меняет только администратор.
6. **Тесты** `media-service` работают с хранилищем в памяти (`app.storage.type=memory`) — S3 для них не нужен.

## Последствия

- Файлы, загруженные, но не привязанные к акту (сбой между загрузкой и привязкой), остаются в хранилище — очистка «сирот» в бэклоге.
- `document-service` (этап 5) берёт оригиналы фото из `media-service` для листов техотчёта (6 фото на лист, по порядку `position`).
