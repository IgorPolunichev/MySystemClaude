## 1. Роль агента и цель проекта

Ты — ведущий Java-архитектор и full-stack разработчик. Твоя задача — спроектировать и реализовать веб-приложение «Сервисные акты» для сервисной компании, которая ремонтирует и обслуживает технику клиентов: от карьерных самосвалов (например, CAT 777) до легковых автомобилей.

Приложение должно:

- формировать акты выполненных работ (АВР) с уникальным номером и выгружать их в Excel (лист 1 — акт, листы 2…N — технический отчёт с фотографиями);
- хранить акты, фото, справочники организаций, отделов, техники, инженеров и запчастей;
- учитывать рабочее время каждого инженера по дням и считать продуктивные часы против нормы;
- искать и сортировать акты, в том числе полнотекстово по всему содержимому акта;
- формировать письма по шаблону со ссылкой на один или несколько актов для получателей из адресной книги;
- закрывать акты с блокировкой редактирования для всех, кроме администраторов;
- выдерживать одновременную работу многих инженеров без потери данных;
- расширяться новыми модулями (уведомления, склад и др.) без переписывания существующего кода.

Главный критерий качества: новый модуль добавляется как новый сервис и новый раздел интерфейса, а существующие сервисы меняются минимально или не меняются вовсе.

## 2. Предметная область и глоссарий

Используй эти термины одинаково в коде (английские имена), API, БД и интерфейсе (русские подписи).

| Термин | Имя в коде | Смысл |
| --- | --- | --- |

| Тип техники | `EquipmentType` | Самосвал, экскаватор, погрузчик, легковой автомобиль и т. д. Справочник. |
| Сервисный инженер | `Engineer` | Сотрудник сервисной компании, выполняющий работы. Связан с пользователем системы. |
| Отдел сервисной компании | `ServiceDepartment` | Подразделение, к которому относится инженер; для него задаётся норма часов. |
| Акт выполненных работ | `WorkAct` | Документ с номером, техникой, работами, временем, запчастями, фото, рекомендациями и подписями. |

| Позиция запчасти | `ActPartLine` | Запчасть или жидкость, использованная в акте: из каталога или введённая вручную. |
| Каталог запчастей | `PartCatalogItem` | Справочник запчастей: наименование, каталожный номер, производитель, единица измерения. |
| Фото техотчёта | `ActPhoto` | Изображение с подписью и порядковым номером, входит в технический отчёт. |
| Норма часов | `HoursNorm` | Плановое количество продуктивных часов в месяц на инженера или на отдел. |
| Шаблон письма | `EmailTemplate` | Текст письма с подстановками для отправки одного или нескольких актов. |
| Адресная книга | `Contact`, `ContactGroup` | Получатели писем и их группы. |

Наработка фиксируется в акте на момент работ (снимок) и одновременно обновляет текущую наработку техники, если новое значение больше прежнего. Данные техники и организации в акте тоже сохраняются снимком, чтобы последующие правки справочников не меняли уже выданные акты.

## 4. Архитектура: микросервисы, границы и взаимодействие

Система строится как набор микросервисов в одном монорепозитории. Сервисов на старте немного: каждый отвечает за одну бизнес-область и владеет своими данными. Ни один сервис не читает чужую БД напрямую.

### Состав сервисов

| Сервис | Ответственность | Владеет данными |
| --- | --- | --- |
| `api-gateway` | Маршрутизация `/api/{service}/**`, проверка JWT, CORS, rate limit, correlation-id | — |
| Keycloak | Пользователи, роли, вход, SSO | Пользователи и роли |
| `directory-service` | Справочники: организации, подразделения, типы техники, техника, инженеры, отделы сервисной компании | Организации, техника, инженеры |
| `parts-service` | Каталог запчастей и жидкостей, единицы измерения, поиск по номеру/названию | Каталог |
| `act-service` | Ядро: акты, нумерация, работы, записи времени, позиции запчастей, метаданные фото, статусы, права, поиск | Акты и всё внутри них |
| `media-service` | Загрузка, хранение, сжатие, превью и выдача файлов (presigned URL) | Объекты в S3-хранилище и их метаданные |
| `document-service` | Генерация Excel по данным акта; профили формы акта (конструктор); в будущем — PDF и другие формы | Шаблоны документов, профили формы акта, история генераций |
| `analytics-service` | Продуктивные часы, нормы, агрегаты для дашборда (read model из событий) | Нормы, агрегаты часов |
| `mail-service` | Адресная книга, шаблоны писем, формирование и отправка писем, журнал отправок | Контакты, шаблоны, журнал |
| `frontend` | SPA, раздаётся через Nginx | — |

Зарезервированы, но не реализуются сейчас: `notification-service` (уведомления: почта, Telegram, push), `warehouse-service` (склад, остатки, приход/расход). Для них уже сейчас публикуются нужные события (см. ниже), чтобы при появлении модулей существующие сервисы не менялись.

### Внутреннее устройство каждого сервиса

Гексагональная архитектура (ports and adapters), пакеты:

```
com.company.acts.<service>
  ├── domain        // сущности, value objects, доменные события, правила; без Spring
  ├── application   // use cases, порты (interfaces), транзакции
  ├── adapter
  │   ├── in.web    // REST-контроллеры, DTO
  │   ├── in.event  // обработчики входящих событий
  │   ├── out.persistence // JPA-репозитории, сущности БД
  │   ├── out.event // публикация через outbox
  │   └── out.client// HTTP-клиенты других сервисов
  └── config
```

Соблюдение слоёв проверяется тестами ArchUnit.

### Общие модули монорепозитория

- `platform-bom` — общие версии зависимостей;
- `common-web` — формат ошибок RFC 7807 (`ProblemDetail`), correlation-id, пагинация, базовая конфигурация безопасности;
- `common-events` — схемы событий (Java `record` + JSON Schema) с полем `eventVersion`;
- `common-test` — базовые классы Testcontainers.

Общие модули не содержат бизнес-логики.

### Взаимодействие

Синхронно (REST через gateway или напрямую по внутренней сети) — когда нужен ответ сейчас: например, `act-service` при создании акта запрашивает у `directory-service` данные техники и сохраняет снимок.

Асинхронно (события через RabbitMQ, outbox, идемпотентные обработчики по `eventId`) — для всего остального:

| Событие | Источник | Кто слушает сейчас | Кто будет слушать позже |
| --- | --- | --- | --- |
| `ActCreated`, `ActUpdated` | act-service | analytics-service | notification-service |
| `ActClosed`, `ActReopened`, ActCancelled | act-service | analytics-service, mail-service | notification-service |
| `TimeEntryChanged` | act-service | analytics-service | — |
| `PartsUsedInAct` (с признаком источника: каталог/вручную) | act-service | parts-service (статистика использования) | warehouse-service (списание) |
| `EquipmentUpdated`, `OrganizationUpdated` | directory-service | act-service (обновление поисковых полей, не снимков) | — |
| `EmailSent` | mail-service | act-service (отметка «отправлен») | notification-service |
| `DocumentGenerated` | document-service | act-service | — |

Каждое событие содержит `eventId`, `eventType`, `eventVersion`, `occurredAt`, `actorId`, `correlationId` и полезную нагрузку. Изменения схем только обратно совместимые; несовместимое изменение — новая версия события.

Все публичные API версионируются префиксом `/api/v1`. Контракт описывается в OpenAPI до реализации (contract-first), из него генерируется TypeScript-клиент фронтенда.

## 5. Модель данных по сервисам

Общие правила для всех таблиц: первичный ключ `UUID` (v7, упорядоченный по времени), поля аудита `created_at`, `created_by`, `updated_at`, `updated_by`, поле `version` для оптимистичной блокировки, мягкое удаление `deleted_at` для справочников. Время хранится в `timestamptz` (UTC), даты работ — в `date`, часы — `numeric(6,2)`, количества — `numeric(12,3)`.

### directory-service

- `organization`: id, name, short\_name, inn, kpp, legal\_address, phone, email, notes, is\_active.
- `department`: id, organization\_id, parent\_id (вложенность), name, code.
- `equipment_type`: id, name (самосвал, экскаватор, легковой и т. д.).
- `equipment`: id, organization\_id, department\_id, equipment\_type\_id, brand, model, serial\_number, garage\_number, plate\_number, meter\_type (`HOURS` | `KM` | `BOTH`), current\_hours, current\_km, year, notes. Уникальность: `serial_number` в пределах организации.
- `service_department`: id, name (отделы сервисной компании).
- `engineer`: id, keycloak\_user\_id, last\_name, first\_name, middle\_name, position, service\_department\_id, phone, email, is\_active.

### parts-service

- `unit_of_measure`: code (`PCS`, `L`, `KG`, `M`, `SET`), name\_ru (шт, л, кг, м, компл.), allows\_fraction.
- `part_catalog_item`: id, name, catalog\_number, manufacturer, default\_unit, is\_fluid, notes. Индексы: trigram по `name` и `catalog_number`. Уникальность: (`catalog_number`, `manufacturer`).

### act-service

- `work_act`: id, act\_number (уникальный), status (`DRAFT` | `OPEN` | `CLOSED` | `CANCELLED`), organization\_id + снимок (name, inn, адрес), department\_id + снимок name, equipment\_id + снимок (brand, model, serial, garage, plate, type), meter\_hours, meter\_km, work\_start\_date, work\_end\_date (вычисляются из записей времени, но могут быть заданы вручную), short\_description (например «ТО-2000»), detailed\_description, recommendations, location (место проведения работ), customer\_mechanic\_name, author\_engineer\_id, closed\_at, closed\_by, sent\_at, search\_vector (`tsvector`), version.
- `act_engineer`: act\_id, engineer\_id, role (`LEAD` | `MEMBER`), снимок ФИО и должности для печати.
- `time_entry`: id, act\_id, engineer\_id, work\_date, start\_time и end\_time (интервал работы), work\_minutes (рассчитанные продуктивные минуты — источник правды), hours (= work\_minutes / 60, округлено до сотых, для отчётов), travel\_hours (необязательно, отдельно от продуктивных), comment. Ограничение: в один день у одного инженера по одному акту — одна запись.
- `time_entry_break`: id, entry\_id, position, start\_time, end\_time — перерывы внутри интервала работы (обед, ожидание).
- `act_part_line`: id, act\_id, position\_no, source (`CATALOG` | `MANUAL` | `WAREHOUSE` — последний зарезервирован), catalog\_item\_id (nullable), name, catalog\_number, quantity, unit\_code, notes.
- `act_photo`: id, act\_id, media\_id, caption, position\_no, taken\_at, uploaded\_by.
- `act_number_sequence`: year, prefix, last\_value — для выдачи номеров.
- `act_history`: id, act\_id, changed\_at, changed\_by, action, diff (`jsonb`) — журнал изменений.
- `outbox`: id, aggregate\_id, event\_type, payload (`jsonb`), created\_at, published\_at.

### media-service

- `media_object`: id, bucket, object\_key, original\_filename, content\_type, size\_bytes, width, height, sha256, thumbnail\_key, owner\_service, owner\_id, created\_by, created\_at.

### document-service

- `document_template`: id, code (`WORK_ACT_XLSX`), version, media\_id шаблона, is\_active.

### analytics-service

- `hours_norm`: id, scope (`ENGINEER` | `SERVICE_DEPARTMENT`), scope\_id, year, month, norm\_hours. Уникальность: (scope, scope\_id, year, month).
- `engineer_daily_hours`: engineer\_id, service\_department\_id, work\_date, productive\_hours, travel\_hours, acts\_count — read model, наполняется из событий `TimeEntryChanged`.
- `processed_event`: event\_id — для идемпотентности.

### mail-service

- `contact`: id, full\_name, email, organization\_name, position, notes, is\_active.
- `contact_group`: id, name; `contact_group_member`: group\_id, contact\_id.

## 6. Функциональные требования: акт, работы, время, запчасти, фото

### 6.1. Номер акта

- Формат по умолчанию: `АВР-{ГГГГ}-{NNNNNN}`, например `АВР-2026-000123`. Префикс и формат настраиваются администратором.
- Номер выдаётся атомарно в `act-service` (`SELECT … FOR UPDATE` по строке `act_number_sequence` текущего года или `UPDATE … RETURNING`), счётчик сбрасывается каждый год. Дубликаты невозможны благодаря уникальному индексу.
- Номер присваивается при переходе акта из `DRAFT` в `OPEN` (черновики нумеруются только временным ID), чтобы в нумерации не было «дыр» от брошенных черновиков. Удалять можно только черновики; открытый акт можно лишь аннулировать (`CANCELLED`) с сохранением номера.

### 6.2. Шапка акта

- Выбор организации → выбор подразделения (фильтр по организации) → выбор техники (фильтр по организации/подразделению, поиск по серийному, гаражному, госномеру, модели).
- Если техники нет в справочнике — кнопка «Добавить технику» в модальном окне без ухода со страницы акта (то же для организации и подразделения).
- В акт копируются (снимок): марка, модель, серийный номер, гаражный номер, госномер, тип техники, наименование и реквизиты организации, наименование подразделения.
- Наработка: моточасы и/или пробег в зависимости от `meter_type` техники. Предупреждение, если введённое значение меньше последнего известного.
- Место проведения работ (необязательно).

### 6.3. Описание работ

- «Краткое описание» — короткая строка до 100 символов (например «ТО-2000», «Замена ГМП»), с автодополнением из ранее использованных значений.
- «Подробное описание выполненных работ» — многострочный текст без жёсткого ограничения (до 10 000 символов).
- «Рекомендации» — многострочный текст для техотчёта.

### 6.4. Инженеры и учёт времени

- В акте один или несколько инженеров; один отмечен как ответственный (по умолчанию — автор акта).
- Время ведётся сеткой «инженер × день»: строки — инженеры, столбцы — даты периода работ. В ячейке инженер указывает **интервал работы** (время начала и окончания, ЧЧ:ММ) и **перерывы** (обед, ожидание запчастей и т. п., любое количество). **Продуктивные часы не вводятся вручную, а рассчитываются**: длительность интервала минус перерывы. Пример: работа с 10:00 до 13:00, обед с 11:00 до 12:00 — 2 ч продуктивного времени. Точность — минута (2 ч 20 мин = 2,33 ч); источник правды — минуты, часы округляются до сотых только для отображения и итогов. Если окончание не позже начала, работа заканчивается на следующий день (ночная смена), часы относятся к дате начала; окончание, равное началу, — ровно 24 ч. Перерывы должны лежать внутри интервала и не пересекаться. Ячейка показывает интервал и рассчитанное время; по нажатию открывается окно ввода с пересчётом на лету и кнопкой «Как в предыдущий день». Дополнительно можно указать время в пути отдельным числом часов (шаг 0,25 ч; в продуктивные часы не входит); запись может состоять только из времени в пути — тогда интервала нет. В акте есть галочка «Скрыть время в пути», по умолчанию она стоит: время в пути хранится и учитывается в аналитике, но не выводится в печатной форме.
- Для длинных работ (недели и месяцы) сетка показывается постранично по неделям с итогами по каждому инженеру и общим итогом. Альтернативный ввод — список записей «дата, инженер, часы, комментарий».
- Проверка: сумма продуктивного времени одного инженера за один день по всем неаннулированным актам не превышает 24 ч (предупреждение при превышении 12 ч).
- Период работ: дата начала и дата окончания вычисляются как минимальная и максимальная дата записей времени; их можно переопределить вручную. Продолжительность отображается в днях (календарных и фактически отработанных).
- Инженер вносит время только за себя; ответственный за акт и администратор — за всех инженеров акта.

### 6.5. Запчасти и жидкости

- Таблица позиций: №, наименование, каталожный номер, количество, единица измерения, примечание.
- Добавление из каталога: поиск по наименованию или номеру с автодополнением; поля заполняются из каталога.
- Ручное добавление: ввод наименования, номера и количества. Флажок «Добавить в каталог», чтобы позиция стала доступна в следующий раз. Без флажка — позиция сохраняется только в акте с `source = MANUAL`.
- Единица измерения выбирается из справочника; для жидкостей — литры с дробными значениями (например 45,5 л). Для штучных позиций дробь запрещена.
- Источник `WAREHOUSE` зарезервирован для будущего модуля склада: тогда позиция будет выбираться из остатков, а событие `PartsUsedInAct` вызовет списание. Сейчас этот вариант в интерфейсе не отображается.
- Возможность вставить список запчастей из буфера обмена (из Excel) — колонки «наименование; номер; количество; ед.».

### 6.6. Фото техотчёта

- Загрузка нескольких файлов сразу (drag-and-drop) и съёмка камерой с телефона.
- Форматы: JPEG, PNG, HEIC (конвертируется в JPEG на сервере). Клиент сжимает до длинной стороны 2560 px; сервер хранит оригинал и превью 400 px.
- Каждое фото обязательно имеет подпись (до 200 символов); порядок меняется перетаскиванием.
- Удаление фото — только пока акт не закрыт.
- Загрузка идёт напрямую в S3-хранилище по presigned URL, выданному `media-service`, а затем акт получает ссылку `media_id`. Ограничение размера одного файла — 20 МБ.

### 6.7. Подписи

- В акте задаются ФИО и должность представителя заказчика (механика), подписывающего акт; ФИО инженеров подставляются из списка инженеров акта.
- В Excel под каждую сторону выводится строка «должность / подпись / ФИО / дата».

### 6.8. Жизненный цикл акта

- `DRAFT` → `OPEN` (присвоение номера) → `CLOSED`; из `OPEN` возможен переход в `CANCELLED`; из `CLOSED` администратор может вернуть в `OPEN` с обязательным комментарием.
- Автосохранение черновика каждые 30 секунд и при уходе со страницы.
- Копирование акта («Создать на основе»): копируются шапка, техника, краткое описание, список запчастей; время и фото не копируются.
- Шаблоны работ (например «ТО-250», «ТО-500», «ТО-2000» для конкретной модели) с типовым описанием и набором запчастей — заполняют акт одним нажатием. Справочник шаблонов ведёт администратор.

### 6.9. Карточки и история

- Карточка техники: все акты по этой машине, история наработки, использованные запчасти.
- Карточка организации: техника по подразделениям, акты, суммарные часы.
- Журнал изменений акта: кто, когда и что изменил (из `act_history`).

## 7. Формирование Excel: лист акта и листы техотчёта

Excel формирует `document-service` на Apache POI (XSSF) по данным, полученным от `act-service` через REST (`GET /api/v1/acts/{id}/document-data` — плоская модель для печати), и файлам фото из `media-service`. Готовый файл сохраняется в S3-хранилище и отдаётся пользователю ссылкой на скачивание.

### Общие правила печати

- Формат A4, книжная ориентация, поля 1,5 см, «вписать по ширине в 1 страницу», шрифт Arial или Calibri 10 pt.
- Логотип и реквизиты сервисной компании в шапке каждого листа (берутся из настроек). Реквизиты исполнителя и заказчика по умолчанию скрыты; состав, порядок и видимость всех блоков и полей определяются профилем формы акта и галочками в акте (раздел 16).
- Колонтитул: номер акта, «Лист X из N».
- Ячейки ввода подписи защищены от случайного редактирования (защита листа без пароля или с паролем из настроек).
- Имя файла: `АВР-2026-000123_CAT777_ГН-45.xlsx`.

### Лист 1 «Акт»

1. Шапка: «Акт выполненных работ № … от …», исполнитель (сервисная компания), заказчик (организация, подразделение).
2. Блок «Техника»: тип, марка, модель, серийный номер, гаражный номер, госномер, наработка (м/ч) и/или пробег (км).
3. Блок «Период работ»: дата начала, дата окончания, продолжительность (дни).
4. «Краткое описание работ» — одна строка.
5. «Подробное описание выполненных работ» — объединённые ячейки с переносом текста; высота строки рассчитывается по объёму текста. Если текст не помещается на лист, он продолжается на дополнительном листе «Акт (продолжение)».
6. Таблица «Исполнители и трудозатраты»: ФИО, должность, количество дней, продуктивные часы итого (рассчитанные из интервалов); время в пути — отдельной колонкой, только если в акте снята галочка «Скрыть время в пути». Подробная разбивка по дням выводится на отдельном листе «Табель», если дней больше 7: по каждому дню — интервал работы, перерывы и продуктивные часы.
7. Таблица «Использованные запчасти и материалы»: №, наименование, каталожный номер, количество, ед. изм.
8. Блок подписей: слева — «Представитель заказчика (механик)», справа — «Сервисный инженер»; для каждого — должность, подпись, ФИО, дата.

### Листы 2…N «Технический отчёт»

1. На каждом листе повторяется шапка: номер акта, дата, организация, техника (марка, модель, серийный, гаражный/госномер, наработка), краткое описание.
2. На первом листе отчёта: «Подробное описание выполненных работ» (как на листе 1) и отдельная графа «Рекомендации».
3. Фото выводятся сеткой 2 столбца × 3 ряда (6 фото на лист; число задаётся в профиле формы, раздел 16) с подписью под каждым и порядковым номером «Фото 1», «Фото 2» и т. д. Фото масштабируются с сохранением пропорций и вписываются в ячейку фиксированного размера. Количество листов = ⌈число фото / 6⌉ (минимум 1 лист, даже без фото, — ради рекомендаций и подписей).
4. На последнем листе отчёта — блок подписей механика и сервисного инженера.
5. Листы называются «Техотчёт 1», «Техотчёт 2» и т. д.

### Шаблоны и расширяемость

- Разметку листа держи в отдельном классе-«рендерере» на каждый лист (`ActSheetRenderer`, `TechReportSheetRenderer`, `TimesheetSheetRenderer`) за общим интерфейсом `SheetRenderer`. Новые листы и форматы (PDF, Word) добавляются новыми реализациями без правки существующих.
- Стили (шрифты, рамки, заливки) вынеси в один класс `ExcelStyles`; тексты подписей полей — в `messages.properties`.
- Сохраняй версию шаблона в `generated_document`, чтобы повторная выгрузка старого акта была воспроизводимой.
- Напиши тест, который генерирует акт с 0, 1, 6, 7 и 23 фото, со скрытыми и показанными реквизитами, с очень длинным описанием и с 30 позициями запчастей, и проверяет количество листов, наличие подписей и отсутствие ошибок POI. Сгенерированные примеры сложи в `docs/samples/` для визуальной проверки.

## 8. Хранение, поиск и сортировка актов

Данные актов лежат в PostgreSQL (`act-service`), фото и сгенерированные файлы — в S3-хранилище (`media-service`). Поиск реализуется в `act-service` средствами PostgreSQL; интерфейс поиска спрятан за портом `ActSearchPort`, чтобы позже заменить реализацию на OpenSearch без правок контроллеров и фронтенда.

### Реестр актов (`GET /api/v1/acts`)

Фильтры (комбинируются):

- период по дате акта или по периоду работ (пересечение интервалов);
- инженер (один или несколько; ищется по участию в акте, а не только по автору);
- организация, подразделение, техника, тип техники, марка/модель;
- статус (черновик, открыт, закрыт, аннулирован), признак «отправлен письмом»;
- краткое описание (точное совпадение или выбор из списка ранее использованных);
- каталожный номер запчасти (найти все акты, где использовалась запчасть);
- полнотекстовый запрос `q` по всему акту.

Сортировка по любому столбцу: номер, дата, организация, техника, краткое описание, ответственный инженер, часы итого, статус. Пагинация серверная (по умолчанию 50 строк), с итоговым числом записей.

### Полнотекстовый поиск

- Поле `search_vector` (`tsvector`, конфигурация `russian`) собирается триггером или в коде при каждом сохранении из: номера акта, краткого и подробного описания, рекомендаций, наименования организации и подразделения, данных техники, ФИО инженеров, наименований и номеров запчастей, подписей к фото. Веса: A — номер и краткое описание, B — техника и организация, C — подробное описание и рекомендации, D — остальное.
- Индекс GIN по `search_vector`; дополнительно индекс `pg_trgm` по серийному, гаражному, госномеру и каталожным номерам — для поиска по части номера и с опечатками.
- Запрос пользователя разбирается через `websearch_to_tsquery('russian', q)`; результаты ранжируются `ts_rank_cd`, совпадения подсвечиваются `ts_headline` в выдаче.

### Экспорт реестра

Кнопка «Выгрузить реестр в Excel» — текущая выборка с фильтрами одной таблицей (без фото).

## 9. Дашборд продуктивных часов и нормы

Продуктивные часы — это сумма рассчитанного продуктивного времени из записей табеля (`time_entry.work_minutes` / 60: интервал работы минус перерывы) по актам в статусах `OPEN` и `CLOSED`; время в пути и аннулированные акты не учитываются. Расчёт и хранение агрегатов — в `analytics-service`, который строит read model из событий `TimeEntryChanged` и `ActCancelled`. Предусмотри эндпоинт полной пересборки агрегатов из `act-service` на случай расхождений.

### Нормы

- Администратор (или руководитель отдела) задаёт норму часов на месяц для каждого инженера и для каждого отдела сервисной компании.
- Массовые операции: «скопировать нормы прошлого месяца», «установить норму всем инженерам отдела».
- Если норма отдела не задана, она считается как сумма норм его инженеров (показывать, что значение вычислено).
- Норма на произвольный период (например квартал) = сумма месячных норм; если период захватывает часть месяца — пропорционально рабочим дням (производственный календарь РФ хранится в справочнике и редактируется администратором).

### Экран дашборда

- Фильтры: период (месяц, квартал, год, произвольный диапазон), отдел, один или несколько инженеров (поиск по ФИО), организация-заказчик.
- Карточки-индикаторы (gauge) по каждому выбранному инженеру и по отделу: факт часов, норма, процент выполнения. Цвета: до 70 % — красный, 70–90 % — жёлтый, от 90 % — зелёный (пороги настраиваются).
- Столбчатая диаграмма «факт против нормы» по инженерам за период.
- Линейный график часов по дням или неделям для выбранного инженера.
- Таблица: ФИО, отдел, норма, факт, %, количество актов, количество машин; клик по строке открывает список актов этого инженера за период.
- Выгрузка таблицы дашборда в Excel.

### Доступ

- Инженер видит только свои показатели.
- Руководитель отдела — свой отдел.
- Администратор — всех.

## 10. Письма, шаблоны и адресная книга

Письма формирует `mail-service`. Пользователь выбирает в реестре один или несколько актов, нажимает «Сформировать письмо», выбирает шаблон и получателей, видит предпросмотр, при необходимости правит текст и отправляет.

### Адресная книга

- Контакты: ФИО, email, организация, должность, примечание; импорт и экспорт CSV.
- Группы получателей (например «Бухгалтерия заказчика X»); выбор группы добавляет всех её участников.
- Поля «Кому», «Копия», «Скрытая копия» с автодополнением из адресной книги и возможностью ввести новый адрес с предложением сохранить его.
- Привязка контактов по умолчанию к организации-заказчику: при формировании письма по актам этой организации получатели подставляются автоматически.

### Шаблоны

- Шаблоны на FreeMarker с переменными: `acts` (список: номер, дата, организация, техника, краткое описание, часы итого), `sender` (ФИО, должность, телефон отправителя), `today`, `totalHours`.
- Тема и тело задаются отдельно; тело — HTML с простым редактором (жирный, списки, таблица актов).
- Шаблон по умолчанию: тема «Акты выполненных работ № …», в теле — таблица актов. Администратор создаёт и редактирует шаблоны.
- Предпросмотр с подстановкой реальных данных до отправки.

### Вложения и способ отправки

- Вложения: Excel-файл каждого выбранного акта (генерируется через `document-service`, если ещё не сформирован или устарел). Если суммарный размер превышает 20 МБ — предупреждение и вариант «архив ZIP» или «ссылки на скачивание вместо вложений».
- Режим 1 (основной): отправка через корпоративный SMTP от общего ящика с адресом пользователя в `Reply-To`.
- Режим 2: скачать готовое письмо `.eml` с вложениями, чтобы открыть и отправить в Outlook из своего ящика.
- Отправленные письма сохраняются в журнале (кому, когда, какие акты, статус). У акта появляется отметка «Отправлен» с датой; повторная отправка разрешена с предупреждением.
- Отправка асинхронная (очередь), с повторами при ошибке SMTP.

Модуль уведомлений в будущем будет переиспользовать адресную книгу и механизм шаблонов, поэтому оформи их как отдельные порты внутри `mail-service` (`TemplateRenderer`, `ContactDirectory`, `MessageSender`), которые позже можно вынести в общий сервис.

## 11. Роли, права и статусы акта

Роли хранятся в Keycloak (realm roles) и приходят в JWT. Проверка прав выполняется на сервере в `application`-слое (класс `ActAccessPolicy`), а не только скрытием кнопок на фронтенде.

| Действие | ENGINEER | DEPARTMENT\_HEAD | ADMIN |
| --- | --- | --- | --- |
| Создать акт | да | да | да |
| Просматривать любые акты | да | да | да |
| Редактировать открытый акт | если он автор или участник акта\* | акты инженеров своего отдела | да |
| Вносить своё время в акт | если участник акта | да | да |
| Закрыть акт (галочка «Закрыт») | если автор\* | да | да |
| Редактировать закрытый акт | нет | нет | да, с обязательным комментарием |
| Вернуть закрытый акт в открытые | нет | нет | да, с обязательным комментарием |
| Аннулировать акт | если автор, пока не закрыт | да | да |
| Справочники: добавлять | да | да | да |
| Справочники: редактировать и удалять | нет | да | да |
| Нормы часов | нет | свой отдел | да |
| Дашборд | свои показатели | свой отдел | все |
| Шаблоны писем, настройки, пользователи | нет | нет | да |

\* По вашему ТЗ редактировать открытый акт может «инженер, который его открыл». Вариант по умолчанию шире: автор и все инженеры, добавленные в акт, — иначе участник не сможет внести своё время. Окончательный вариант см. в разделе «Допущения».

### Правила закрытия

- Закрыть можно только акт в статусе `OPEN` с заполненными обязательными полями: техника, наработка, краткое описание, хотя бы одна запись времени.
- После закрытия все изменяющие эндпоинты для ролей ниже ADMIN возвращают `403` с понятным сообщением; фронтенд показывает акт в режиме только чтения с плашкой «Акт закрыт {дата}, {кто}».
- Любое изменение закрытого акта администратором фиксируется в `act_history` с комментарием и событием `ActUpdated` с признаком `afterClose = true`.
- Массовое закрытие: выбрать несколько актов в реестре → «Отметить как закрытые».

## 12. Нефункциональные требования

### Одновременная работа

- Оптимистичная блокировка на всех изменяемых агрегатах (`@Version`). Клиент передаёт версию в заголовке `If-Match` (ETag); при конфликте сервер отвечает `409 Conflict` с текущей версией данных, фронтенд показывает «Акт изменён другим пользователем» и предлагает обновить или сравнить изменения.
- Записи времени разных инженеров в одном акте не конфликтуют друг с другом: время сохраняется отдельными запросами по строке `time_entry`, а не перезаписью всего акта.
- Индикатор «Сейчас акт редактирует: Иванов И. И.» (мягкая блокировка с TTL 2 минуты, обновляется пингом) — информирует, но не запрещает.
- Нумерация актов и уникальные ограничения защищены на уровне БД.

### Производительность и объёмы (ориентиры)

- До 200 одновременных пользователей, до 50 000 актов в год, до 1 млн фото за 5 лет.
- Реестр с фильтрами и полнотекстовым поиском — ответ до 500 мс на 95-м перцентиле.
- Генерация Excel с 40 фото — до 15 секунд; выполняется асинхронно со статусом задачи, если дольше 3 секунд.

### Безопасность

- Только HTTPS; JWT с коротким сроком жизни и refresh-токеном; CORS только для домена фронтенда.
- Проверка типа загружаемых файлов по содержимому (Apache Tika), ограничение размера, удаление EXIF-геоданных по настройке.
- Доступ к файлам в S3-хранилище только через presigned URL с коротким сроком жизни.
- Секреты — через переменные окружения или Vault/Kubernetes Secrets, не в репозитории.
- Зависимости проверяются OWASP Dependency-Check или Trivy в CI.

### Аудит и надёжность

- Журнал изменений актов (`act_history`) и журнал входов (Keycloak events).
- Ежедневные резервные копии БД и бакета, тест восстановления описан в `docs/ops/backup.md`.
- Health checks (Spring Actuator), готовность и живость для оркестратора.
- Единый формат ошибок RFC 7807 с русскоязычным `detail` для пользователя.
- Сквозной `correlationId` в логах, событиях и трассировке.

### Качество кода

- Покрытие юнит- и интеграционными тестами доменной и прикладной логики не ниже 80 %.
- Интеграционные тесты с Testcontainers для каждого сервиса; контрактные тесты между сервисами.
- Сквозные тесты Playwright для ключевых сценариев: создать акт → добавить время двух инженеров за три дня → добавить запчасти (каталог, вручную, литры) → загрузить 5 фото → выгрузить Excel → отправить письмо → закрыть → проверить запрет редактирования.
- Документация: `README.md` (запуск за одну команду), `docs/architecture.md` с C4-диаграммами (PlantUML или Mermaid), ADR на ключевые решения в `docs/adr/`.

## 13. Правила расширяемости

Цель: новый модуль (уведомления, склад, учёт выездов, PDF-акты, мобильное приложение) добавляется без переписывания существующего. Соблюдай эти правила во всём коде.

1. Новый модуль = новый сервис со своей БД, подписанный на уже существующие события. Существующие сервисы не знают о подписчиках.
2. События публикуются «с запасом»: всё значимое, что происходит с актом, уже сейчас уходит в шину, даже если слушателя пока нет.
3. Контракты (OpenAPI, схемы событий) меняются только обратно совместимо: новые поля — необязательные, старые не удаляются и не переименовываются. Ломающее изменение — новая версия `/api/v2` или `eventVersion: 2` с параллельной поддержкой старой.
4. Точки расширения оформляются интерфейсами со стратегиями: `SheetRenderer` (листы документа), `DocumentFormat` (xlsx, pdf), `PartSource` (каталог, вручную, склад), `MessageSender` (SMTP, позже Telegram/push), `ActSearchPort` (PostgreSQL, позже OpenSearch).
5. Поля, которых пока нет, но которые точно понадобятся, закладываются в модель как nullable (например `source = WAREHOUSE`, `warehouse_item_id`).
6. Пользовательские атрибуты: таблица `custom_field_definition` + колонка `custom_fields jsonb` у техники и акта, чтобы администратор мог добавить поле (например «Номер заявки заказчика») без миграции и релиза.
7. Фронтенд построен из модулей-фич (`src/features/acts`, `src/features/dashboard`, `src/features/mail`, …). Каждый модуль экспортирует свои маршруты и пункты меню в общий реестр `moduleRegistry.ts`; новый модуль подключается одной строкой.
8. Флаги функций (feature flags) в конфигурации, чтобы включать модули поэтапно.
9. Права описываются через permissions (`act:edit`, `act:close`, `norm:edit`), а роли — набором permissions. Новый модуль добавляет свои permissions без изменения существующих ролей.
10. Каждое архитектурное решение фиксируется в ADR с указанием, как расширять.

## 14. Фронтенд

Фронтенд — одностраничное приложение на React + TypeScript + Ant Design. Этот выбор сделан потому, что приложение по сути «учётное»: много таблиц, фильтров и сложных форм, а Ant Design даёт всё это готовым и с русской локалью. React — самый распространённый стек, по нему проще найти разработчика и ИИ-агенты пишут на нём надёжнее всего. Интерфейс полностью на русском языке, адаптивный: инженер работает с ноутбука в офисе и с телефона у машины.

### Структура проекта

```
frontend/
  src/
    app/          // провайдеры, маршруты, layout, moduleRegistry.ts
    api/          // сгенерированный Orval клиент (не править руками)
    shared/       // UI-компоненты, хуки, утилиты, форматтеры
    features/
      acts/       // реестр, карточка, редактор акта
      directory/  // организации, подразделения, техника, инженеры
      parts/      // каталог запчастей
      dashboard/  // часы и нормы
      mail/       // адресная книга, шаблоны, отправка
      admin/      // пользователи, настройки, нормы, шаблоны работ
```

### Экраны

1. **Реестр актов** — таблица с фильтрами в панели слева/сверху, строкой полнотекстового поиска, сохраняемыми наборами фильтров, множественным выбором (закрыть, отправить письмом, выгрузить) и цветовыми метками статусов.
2. **Редактор акта** — вкладки или шаги: «Шапка и техника» → «Работы» → «Исполнители и время» → «Запчасти» → «Фото и рекомендации» → «Подписи и выгрузка». Боковая панель с итогами (часы, дни, число запчастей и фото) и кнопками «Сохранить», «Выгрузить Excel», «Отправить», «Закрыть акт». Индикатор автосохранения.
3. **Сетка времени** — таблица «инженер × день»: в ячейке интервал работы и рассчитанные часы; по нажатию — ввод начала, окончания и перерывов с пересчётом на лету; итоги по строкам и столбцам, переключение недель.
4. **Фото** — галерея с drag-and-drop загрузкой, сменой порядка перетаскиванием, полем подписи под каждой миниатюрой, просмотром в полный размер; на телефоне — кнопка «Сделать фото».
5. **Справочники** — организации с деревом подразделений, техника с карточкой и историей актов, инженеры, каталог запчастей.
6. **Дашборд** — фильтры, индикаторы-«спидометры», графики и таблица (раздел 9).
7. **Почта** — мастер «Сформировать письмо», адресная книга, шаблоны, журнал отправок.
8. **Администрирование** — конструктор форм актов (раздел 16), нормы, шаблоны работ, формат номера акта, реквизиты и логотип компании, производственный календарь, пользовательские поля.

### Правила для фронтенда

- Весь доступ к API — только через сгенерированный клиент и TanStack Query; никаких «ручных» `fetch`.
- Права на кнопки берутся из permissions пользователя, но сервер всё равно проверяет их сам.
- Тексты интерфейса вынести в файлы локализации (`i18next`), даже если язык один, — чтобы позже не искать строки по коду.
- Светлая и тёмная тема через токены Ant Design.
- Мобильная версия редактора акта: одна колонка, крупные элементы, ввод времени и фото в приоритете; работа без связи — по разделу 17.

## 16. Конструктор формы акта и скрытие реквизитов

Состав и вид акта настраиваются без программирования. Администратор задаёт в конструкторе «профили формы»: какие блоки и поля показывать, в каком порядке и с какими подписями. Инженер в конкретном акте может дополнительно скрыть или показать отдельные элементы галочками. Не у каждой техники есть все данные (у карьерного самосвала нет госномера, у легкового автомобиля нет моточасов), поэтому лишние строки не должны попадать в акт.

### 16.1. Скрытие реквизитов компаний

- В каждом акте есть галочка «Скрыть реквизиты компаний». **По умолчанию она стоит** у всех новых актов.
- Когда галочка стоит, в Excel и предпросмотре от исполнителя и заказчика выводится только наименование. Скрываются ИНН, КПП, ОГРН, юридический и фактический адрес, банковские реквизиты, телефоны и email.
- Логотип сервисной компании — отдельный элемент конструктора со своей настройкой видимости.
- Значение галочки по умолчанию задаётся в профиле формы; в поставке оно равно «скрыть».

### 16.2. Профиль формы акта

Профиль — это набор блоков, каждый блок содержит поля. Для каждого блока и поля настраиваются:

| Настройка | Значения | Пример |
| --- | --- | --- |
| Видимость | показать / скрыть | Скрыть «Госномер» для карьерной техники |
| Порядок | перетаскиванием | «Гаражный номер» выше «Серийного номера» |
| Подпись | свой текст | «Наработка» → «Моточасы» |
| Скрывать, если пусто | да / нет (по умолчанию да) | Пустое «Место работ» не печатается |
| Обязательно для закрытия акта | да / нет | Наработка обязательна |
| Можно менять в акте | да / нет | Инженер не может скрыть подписи |

Блоки (сверху вниз по умолчанию): логотип; реквизиты исполнителя; реквизиты заказчика; подразделение; техника; наработка; период работ; место работ; краткое описание; подробное описание; исполнители и трудозатраты; время в пути; табель по дням; запчасти и материалы; рекомендации; фото; подписи.

Настройки технического отчёта в профиле: число фото на листе (4 или 6, по умолчанию 6), какие поля шапки повторять на каждом листе, выводить ли подробное описание и рекомендации.

### 16.3. Выбор профиля

- В поставке есть системный профиль по умолчанию; администратор может создавать любое число профилей, например «Карьерная техника» (гаражный номер, моточасы) и «Легковые автомобили» (госномер, пробег).
- Профиль назначается автоматически по правилам, от более частного к общему: организация + тип техники → организация → тип техники → системный профиль.
- Инженер может сменить профиль в акте вручную из списка.

### 16.4. Настройки в конкретном акте

- В редакторе акта, в разделе «Подписи и выгрузка», показывается список блоков и полей текущего профиля с галочками «Показывать в акте». Менять можно только элементы, где профиль это разрешает.
- Галочки по умолчанию: «Скрыть реквизиты компаний» — стоит; «Скрыть время в пути» — стоит; остальное — как в профиле.
- Эти галочки влияют только на печатную форму; данные в базе сохраняются полностью и участвуют в поиске и дашборде.
- Предпросмотр акта обновляется сразу после изменения галочек.

### 16.5. Хранение и воспроизводимость

- Профили хранит `document-service`: `act_form_profile` (id, name, is\_default), `act_form_profile_version` (profile\_id, version, layout `jsonb`, created\_by, created\_at), `act_form_profile_binding` (profile\_id, organization\_id, equipment\_type\_id, priority).
- `act-service` хранит в акте `form_profile_id`, `display_overrides jsonb` (галочки акта) и при закрытии — `layout_snapshot jsonb` (итоговую раскладку), чтобы повторная выгрузка закрытого акта была точно такой же даже после правки профиля.
- Структура `layout` описывается JSON Schema в `common-events`; изменение профиля создаёт новую версию, старые версии не меняются.

### 16.6. Реестр полей и расширяемость

- Все поля, доступные конструктору, перечислены в коде в одном реестре `FieldRegistry` с ключами вида `equipment.garageNumber`, `act.travelHours`, `customer.inn`, их типом и подписью по умолчанию.
- Пользовательские поля (раздел 13, п. 6) автоматически попадают в реестр и становятся доступны конструктору.
- Рендереры Excel (`SheetRenderer`) и редактор акта на фронтенде строятся не на жёстко заданных полях, а на вычисленной раскладке `EffectiveLayout` = профиль + галочки акта + правило «скрывать, если пусто». Новое поле или блок появляется в акте после добавления в реестр, без правки рендереров.

### 16.7. Интерфейс конструктора

- Раздел «Администрирование → Формы актов»: список профилей, кнопки «Создать», «Копировать», «Назначить».
- Редактор профиля: слева дерево блоков и полей с переключателями и перетаскиванием (библиотека `dnd-kit`), справа живой предпросмотр листа акта и листа техотчёта на демонстрационных данных; кнопка «Скачать пример Excel».
- Право `form-profile:edit` — только у администратора.

## 17. Офлайн-режим

Инженер должен работать с актами без интернета (на карьере, в боксе, в удалённом районе), а при появлении связи данные синхронизируются автоматически. Офлайн-режим реализуется в PWA. Заделы под него закладываются с этапа 3: идентификаторы, создаваемые на клиенте, и идемпотентные API. Без них офлайн потом придётся встраивать с переделкой ядра.

### 17.1. Что работает без связи

| Работает офлайн | Только онлайн |
| --- | --- |
| Создание и редактирование актов (шапка, описания, рекомендации) | Присвоение постоянного номера акта |
| Ввод времени по дням | Закрытие акта и возврат в открытые |
| Запчасти из кэша каталога и вручную | Формирование Excel и отправка писем |
| Съёмка и загрузка фото с подписями (в очередь) | Дашборд и нормы |
| Просмотр своих актов за последние 90 дней и справочников | Полнотекстовый поиск по всей базе (офлайн — поиск по локальным данным) |
| Добавление новой техники и организации (в очередь) | Администрирование и конструктор форм |

### 17.2. Технологии на клиенте

- `vite-plugin-pwa` + Workbox: предварительное кэширование оболочки приложения, стратегии кэширования для API-справочников.
- Dexie.js (обёртка над IndexedDB): локальная база с таблицами актов, записей времени, позиций запчастей, фото (Blob), справочников и очереди операций.
- Очередь синхронизации (клиентский outbox): каждая операция записывается как `{opId, entity, entityId, baseVersion, payload, createdAt}` и отправляется по порядку.
- Background Sync API там, где он поддерживается; в остальных браузерах (iOS Safari) — синхронизация при восстановлении сети, при открытии приложения и по кнопке.
- `navigator.storage.persist()` и контроль квоты с предупреждением, когда место заканчивается.

### 17.3. Загрузка данных на устройство

- При входе и затем периодически загружаются: организации и подразделения, техника, каталог запчастей, инженеры, профили формы акта, акты пользователя за 90 дней (глубина настраивается).
- Для больших справочников администратор может ограничить загрузку организациями, за которыми закреплён инженер.
- Обновление дельтами: каждый сервис предоставляет `GET …?updatedSince=<timestamp>` и возвращает изменённые записи и список удалённых id (tombstones). Поэтому у всех синхронизируемых сущностей должно быть мягкое удаление.

### 17.4. Идентификаторы и номера

- Все создаваемые сущности (акты, записи времени, позиции, фото, новая техника) получают UUID v7 на клиенте. Эндпоинты создания идемпотентны: `PUT /…/{id}` или заголовок `Idempotency-Key`; повтор той же операции не создаёт дубль.
- Акт, созданный офлайн, находится в статусе `DRAFT` с временным номером `Ч-{код устройства}-{n}`. Инженер может отметить «Открыть после синхронизации»; постоянный номер `АВР-…` выдаётся сервером при синхронизации, и пользователь видит уведомление о присвоенном номере.

### 17.5. Конфликты

- Каждая операция несёт `baseVersion`. Если версия на сервере совпадает — изменение применяется.
- Записи времени, позиции запчастей и фото — отдельные сущности, поэтому правки разных инженеров одного акта почти не конфликтуют.
- Если поля акта изменены и на сервере, и на устройстве, сервер возвращает `409` с серверной версией. Клиент сохраняет конфликт и показывает экран сравнения по полям: «оставить моё», «оставить серверное», выбрать по каждому полю.
- Если акт был закрыт на сервере, пока инженер работал офлайн, его изменения отклоняются, сохраняются локально как «Отклонённые изменения» и могут быть переданы администратору одной кнопкой.

### 17.6. Фото офлайн

- Фото сжимаются на устройстве и хранятся в IndexedDB до отправки.
- При появлении связи загружаются в фоне по presigned URL с повтором при обрыве; крупные файлы — частями (S3 multipart).
- В галерее у каждого фото виден статус: «на устройстве», «загружается», «загружено».

### 17.7. Интерфейс

- Постоянный индикатор в шапке: «Онлайн» / «Офлайн», счётчик неотправленных изменений, кнопка «Синхронизировать сейчас».
- Журнал синхронизации: что отправлено, что ждёт, какие ошибки и конфликты.
- При выходе из учётной записи с неотправленными данными — предупреждение и запрет очистки до синхронизации или явного подтверждения.

### 17.8. Безопасность офлайн

- Работа офлайн разрешена с просроченным access-токеном в пределах офлайн-сессии (по умолчанию 7 дней, настраивается). При появлении сети токен обновляется; если refresh-токен истёк — повторный вход, после чего очередь отправляется.
- Выход из учётной записи очищает локальную базу.
- Сервер заново проверяет права на каждую операцию из очереди.

### 17.9. Тестирование и риски

- Сквозные тесты Playwright в режиме `offline`: создать акт без сети, внести время и 6 фото, восстановить сеть, проверить номер, данные и фото на сервере; сценарий конфликта двух инженеров.
- Риск: iOS Safari может очищать хранилище неиспользуемых сайтов и не поддерживает фоновую синхронизацию. Если ограничения PWA окажутся критичными, мобильный клиент можно позже сделать нативным (Flutter или React Native) на тех же API синхронизации; серверная часть при этом не меняется.
